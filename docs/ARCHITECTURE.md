# Архитектура

## Задача, которую решает схема

Обычный веб-шелл держит SSH-соединение внутри HTTP-процесса. Последствия предсказуемы:
перезапуск сервиса (деплой, `systemctl restart`, OOM) рвёт все терминалы; F5 в браузере
теряет всё, что было на экране; `known_hosts`, креды и история живут в localStorage.

Здесь SSH вынесен из веб-слоя. Отсюда три требования, которые задают всю конструкцию:

1. закрыл вкладку — терминал жив;
2. перезапустил веб-слой — терминал жив;
3. упал/убит процесс сессии — вывод, который уже был на экране, остался в истории.

Четвёртое — «перезагрузили весь хост» — физически недостижимо для живого TCP-соединения.
Это записано как ограничение и отдельный путь восстановления (ADR-006), а не как обещание.

## Процессы

```
┌────────────────┐   REST: хосты, креды, история, состояние UI
│ браузер        │──────────────────────────────────────────────┐
│  xterm.js      │   WS: кадры терминала (ввод/вывод)           │
└────────────────┘──────────────┬───────────────────────────────┘
                                ▼
                    ┌───────────────────────┐        spawn (detached)
                    │ веб-слой (fastify)    │───────────────┐
                    │  · авторизация        │               │
                    │  · CRUD кред/хостов   │               │
                    │  · прокси WS→сокет    │               │
                    └───────────┬───────────┘               ▼
                                │              ┌──────────────────────────┐
                    SQLite (WAL)│              │ воркер сессии (1 на SSH) │
                    один файл   │              │  · ssh2 Client           │
                                └─────────────►│  · ring-буфер (512 КиБ)  │
                                               │  · запись истории в БД   │
                                               │  · unix-сокет на сессию  │
                                               └────────────┬─────────────┘
                                                            │ ssh2
                                                            ▼
                                                     удалённый хост
```

Почему воркер, а не «поток/пул соединений в вебе»: воркер — граница отказа. Упавший SSH
уносит один терминал, а не все; обновление веб-кода не требует разрывать соединения;
`SIGKILL` веб-слоя не виден воркерам, потому что они `detached` и не делят с ним ни группу
процессов, ни пайпы.

Почему воркер, а не tmux на целевой машине: tmux нужно ставить на каждый хост, он меняет
окружение пользователя и не спасает при падении самого SSH-соединения — сессия перестаёт
быть «моей ssh-сессией» и становится «их tmux-сессией». Здесь сохраняется именно SSH.

## Протокол между слоями

Единый формат на всех участках: `[4 байта BE длина][1 байт тип][payload]`, `src/proto/frames.ts`.

| тип | значение | payload |
| --- | --- | --- |
| 1 | control | JSON, дискриминант `t` |
| 2 | out | байты вывода терминала (как есть) |
| 3 | in | байты ввода (как есть) |

Вывод не кодируется в base64: escape-последовательности, UTF-8 и бинарный мусор от программ
должны доезжать байт-в-байт, а base64 раздувает поток на треть и рвёт кадры в неудачных местах.

Control-сообщения: `hello`, `attach{from}`, `attached{fromSeq,replayedBytes}`, `resize`,
`detach`, `status`, `exit`, `error`, `ping/pong`. Клиентский `out` не принимается — иначе
браузер мог бы инжектить в терминал чужой вывод.

Границы кадров = границы ws-сообщений: веб-слой перекадрирует поток воркера, чтобы фронтенд
не занимался склейкой половинок кадра.

## Хранение

SQLite, один файл, WAL и `synchronous = FULL`. Это осознанный выбор: коммит подтверждается
только после fsync, поэтому «пропало питание» не стирает последние секунды истории. Цена —
меньшая пропускная способность записи, поэтому вывод пишется пачками (25 мс или 64 КиБ).

| таблица | зачем |
| --- | --- |
| `users`, `auth_sessions` | вход; в БД лежит хеш токена cookie, не токен |
| `credentials` | шифротекст + `aad` = `credential:<id>:<user_id>` |
| `hosts` | адрес, пользователь, ссылка на креды, метки |
| `sessions` | одна строка = один SSH-канал: pid, сокет, seq, статус, `ended_at` |
| `session_chunks` | история вывода: `(session_id, seq, dir)` — то, из чего восстанавливается экран |
| `ui_state` | раскладка вкладок и темы per user+device |
| `audit_log` | кто вошёл, кто куда подключался (без значений секретов) |

Ретенция: не больше `WEB_SSH_SCROLLBACK_BYTES` (по умолчанию 8 МиБ) на сессию, старые чанки
удаляются первыми. В памяти воркера — ring на `WEB_SSH_RING_BYTES` (512 КиБ) для мгновенной
перерисовки; если клиент просит `from` старше ring, веб-слой отдаёт историю из БД
(`GET /api/sessions/:id/scrollback`).

## Отказоустойчивость по уровням

| Что произошло | Что с терминалом | Как восстанавливается |
| --- | --- | --- |
| F5 / закрыл вкладку | жив в воркере | reconnect: `attach{from: lastSeq}` + история из БД |
| `systemctl restart web-ssh` | жив | воркеры `detached`, сокеты не тронуты |
| `SIGKILL` веб-слоя | жив | то же; сверка при следующем старте |
| `SIGKILL` воркера | канал умирает | история до последнего коммита; сессия → `lost` |
| сбой записи БД | терминал работает | вывод остаётся в ring; ошибка видна в логе, не молча |
| перезагрузка хоста | канал умирает (TCP) | сессии → `lost` при старте; восстановление окружения — ADR-006 |
| пропало питание | последний коммит цел | WAL + `synchronous=FULL` |

Живость определяется подключением к Unix-сокету (`isSocketAlive`), а не файлом и не статусом
в БД: после `SIGKILL` файл сокета остаётся на диске, и проверка «файл есть» врёт.

## Безопасность

- Пароль владельца — scrypt (N=2^15, r=8, p=1), параметры в строке хеша → можно поднять позже.
- Cookie: `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS; в БД хеш токена.
- Креды: AES-256-GCM, ключ в отдельном файле 0600, `aad` привязывает запись к владельцу.
  Подмена строки в БД или копирование конверта в чужую запись ломает расшифровку.
- Секреты не попадают ни в argv (воркер читает их из БД сам), ни в логи, ни в ответы API.
- Медленный клиент рвётся, когда его буфер превышает 16 МиБ: иначе один зависший браузер
  съедает память, в которой живут чужие сессии.

Осознанно не сделано (см. ADR): сверка `known_hosts`, TOTP, ограничение частоты входов на
уровне приложения (сейчас — задача прокси), шифрование БД целиком, `in`-журнал ввода.
