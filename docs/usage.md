# Как пользоваться

Инструкция для того, кто **заходит** в уже установленный клиент: вход, креды, хосты, консоли,
что означают ошибки. Установка на сервер — `docs/deploy.md`, устройство внутри —
`docs/ARCHITECTURE.md`.

## Что это

Терминал SSH в браузере. Ключевое отличие от обычного «веб-шелла»: SSH-соединение живёт
в отдельном процессе на сервере, поэтому закрытая вкладка, F5 и перезапуск самого сервиса
консоль не убивают.

Чего здесь нет: передачи файлов (SFTP/SCP), проброса портов, split-screen, мультиплексирования
через tmux (ADR-006), проверки ключа удалённого хоста (ADR-007) и второй фактор для входа (TOTP).
Если что-то из этого нужно — это делается в обычном `ssh`, а не здесь.

## Вход

Замков два, и это разные учётки — их легко перепутать.

1. **Basic-auth на прокси** (на публичном инстансе). Браузер покажет системное окно
   «Введите имя пользователя и пароль» ещё до загрузки страницы. Это не форма приложения:
   логин и пароль здесь задаёт администратор в `/etc/nginx/.dev_htpasswd`. Обычно браузер
   запоминает их сам.
2. **Учётка приложения** — форма «Вход» с полями `логин` и `пароль`. Хранится в БД сервиса,
   пароль лежит хешем `scrypt`.

Первый вход на свежей установке — не «Вход», а **«Создать владельца»**: пока в БД нет
ни одного пользователя, форма открыта. После этого регистрация закрывается администратором
(`WEB_SSH_ALLOW_REGISTRATION=false`), и новых учёток через интерфейс не появляется.

Выход — кнопка ⏻ в правом верхнем углу. Она снимает cookie-сессию на этом устройстве;
SSH-сессии при этом продолжают жить на сервере.

Cookie живёт `WEB_SSH_AUTH_SESSION_DAYS` (по умолчанию 30 дней). На боевой установке стоит
`WEB_SSH_COOKIE_SECURE=true`, то есть cookie уходит только по HTTPS: если открыть тот же
сервис по `http://`, вход «не запомнится» — это не баг, а этот флаг.

## Экран

| Элемент | Что делает |
| --- | --- |
| `⚙` в шапке | панель «Хосты и креды» — единственное место, где что-то настраивается |
| `⏻` в шапке | выход из учётной записи приложения |
| `☰` (на телефоне) | выдвигает рельс: сессии и хосты |
| Рельс слева | сверху сессии, снизу хосты; клик по сессии открывает вкладку, клик по хосту — новую консоль |
| `+ Новая консоль` | подсказывает, что консоль открывается кликом по хосту в рельсе |
| Вкладки | открытые консоли; закрытие вкладки **не** закрывает SSH |
| Статусбар внизу | хост сессии, размер терминала, номер последнего кадра, режим |
| Панель клавиш (телефон) | Esc, Tab, ^C, ^D, ^Z и стрелки — на мобильной клавиатуре их нет |

## Шаг 1. Креды

`⚙` → блок «Креды». Порядок важен: креды создаются **до** хоста, потому что хост на них
ссылается.

| Поле | Что писать |
| --- | --- |
| Метка | как вы будете узнавать креды: `vps-root`, `dmn@notebook` |
| Тип | `пароль` или `приватный ключ` |
| Секрет | пароль либо **весь** файл приватного ключа, со строками `BEGIN` и `END` |
| Парольная фраза ключа | если ключ с фразой; для пароля поле оставить пустым |

Пароль или ключ уходят на сервер по HTTPS и там шифруются (AES-256-GCM, ключ хранится
отдельным файлом вне БД). **Обратно интерфейс их не отдаёт никогда** — ни в списке, ни в
ответе API. Поэтому «посмотреть, что я ввёл» нельзя: ошибка = удалить креды и создать заново.

### Ключ вместо пароля

Пароли в этом клиенте работают, но ключ лучше: его можно отозвать, не меняя пароль на хосте,
и он не переживает утечку текстом.

На машине, откуда удобно администрировать (не обязательно на сервере с клиентом):

```bash
ssh-keygen -t ed25519 -a 100 -C "web-ssh-client" -f ~/.ssh/webssh_myserver
ssh-copy-id -i ~/.ssh/webssh_myserver.pub user@myserver
```

Если `ssh-copy-id` не подходит (нет пароля, парольный вход выключен, хост — эта же машина),
публичную часть добавляют вручную:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat ~/.ssh/webssh_myserver.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Проверка, что ключ рабочий, **до** заведения кредов в интерфейсе:

```bash
ssh -i ~/.ssh/webssh_myserver -o IdentitiesOnly=yes user@myserver 'echo ok'
```

Не добавляйте в `authorized_keys` опцию `restrict`: она запрещает выделение PTY, и терминал
в браузере не поднимется (вход пройдёт, консоль останется пустой). Нужны только
`no-port-forwarding,no-agent-forwarding,no-X11-forwarding,pty`.

Порядок в форме: тип → `приватный ключ`, в секрет — файл целиком, в поле фразы — парольную
фразу. Если оставить тип `пароль`, ключ сохранится как пароль и сессия упадёт на
аутентификации.

## Шаг 2. Хост

Всё в той же панели `⚙`, блок «Хосты».

| Поле | Пример | Замечание |
| --- | --- | --- |
| Метка | `notebook` | как хост будет называться в рельсе |
| Адрес | `127.0.0.1` или `host.example.com` | имя или IP |
| Порт | `22` | по умолчанию 22 |
| Пользователь | `dmn` | системная учётка на целевом хосте, не учётка приложения |
| Креды | выбрать из списка | если список пуст или только «без кредов» — шаг 1 не сохранён |
| Заметка | необязательно | для себя |

Удаление хоста и кредов — ссылкой «удалить» на соответствующей строке в списке. Живую сессию
удаление хоста не рвёт: SSH-процесс уже установлен и работает, пока вы его не завершите или
пока оболочка не выйдет. А удаление кредов оставляет хост без кредов: новые консоли к нему
не поднимутся, пока не создать другие и не назначить их хосту.

## Шаг 3. Консоль

Клик по хосту в рельсе. Открывается вкладка, внутри — обычный `xterm`: работает всё, что
работает в терминале, включая `vim`, `htop`, `tmux`, цвета и мышь, если их поддерживает
приложение на хосте.

- **Несколько консолей** — по вкладке на каждую; у каждой свой SSH-процесс на сервере.
- **F5 / закрыл вкладку браузера** — сессия остаётся на сервере, вкладки и активная позиция
  восстанавливаются из сохранённого состояния. Вывод, который пришёл пока вас не было,
  прокручивается из истории на сервере.
- **Два устройства** (телефон + ноутбук) — можно открыть обе и смотреть одну и ту же сессию.
- **Копирование** — выделить мышью и взять из контекстного меню «Копировать» (или `Ctrl+Shift+C`
  в браузере, если он это поддерживает). `Ctrl+C` в терминале — это `SIGINT` для программы
  на хосте, а не копирование. Вставка — `Ctrl+Shift+V` либо средняя кнопка мыши; на телефоне —
  обычное долгое нажатие.
- **Завершить сессию** — кнопка `⏻` на строке сессии в рельсе (SSH-канал закрывается,
  процессы на хосте получают SIGHUP). Закрытие вкладки — не то же самое.

Порядок открытия вкладок и активная вкладка запоминаются на сервере по устройству, поэтому
после перезагрузки страницы всё возвращается как было.

## Состояния сессии

| Статус в рельсе | Что значит | Что делать |
| --- | --- | --- |
| подключено | канал SSH открыт, есть привязанный клиент | — |
| в фоне | канал SSH жив, браузер отключился | открыть вкладку снова, вывод не потерян |
| завершено | оболочка на хосте вышла (`exit`, `^D`) | открыть новую консоль |
| потеряно | процесс сессии умер или хост перезагрузился | открыть новую консоль; вывод до потери читается из истории |

`потеряно` — честное состояние, а не сбой интерфейса: клиент не притворяется, что сессия жива.
После перезагрузки **целевого** хоста сессию не восстановить (это ADR-006; путь —
поле команды запуска с `tmux`, ещё не сделано).

## Ошибки

| Сообщение | Причина | Что делать |
| --- | --- | --- |
| системное окно basic-auth снова и снова | неверный логин/пароль прокси | взять у администратора, не путать с учёткой приложения |
| `неверный логин или пароль` | учётка приложения | проверить логин; восстановления пароля через интерфейс нет — только администратор |
| `429` в ответ на вход | сработал rate limit прокси (`10 r/m`, burst 5) | подождать минуту, не долбить |
| `SSH: All configured authentication methods failed` | ключ не тот, не тот пользователь, парольная фраза неверна, ключ не в `authorized_keys` | проверить тем же ключом обычным `ssh -i`; креды правкой не обновляются — пересоздать |
| `Cannot parse privateKey` | ключ вставлен обрезанным, с `\r` (копирование из Windows-редактора) либо это формат, который `ssh2` не читает | вставить файл целиком, от `BEGIN` до `END` |
| `SSH: Timed out while waiting for handshake` | до хоста нет сети или порт закрыт | `nc -vz host 22` с сервера клиента |
| сессия сразу `потеряно` | `sshd` на хосте отклонил соединение, либо процесс не смог стартовать | смотреть `journalctl -u web-ssh` на сервере клиента |
| `SSH: Host denied (keyboard-interactive)` | на хосте включён только `keyboard-interactive` | нужен ключ или настройка `sshd` на хосте |

Текст ошибки приходит в терминал как обычный вывод, поэтому он же остаётся в истории сессии.

## Доступ и отзыв

Что где лежит:

| Секрет | Где | Кому доступно |
| --- | --- | --- |
| пароль basic-auth | `/etc/nginx/.dev_htpasswd` (хеш) | root |
| пароль учётки приложения | БД сервиса, хеш `scrypt` | root |
| пароль/ключ SSH к хостам | БД сервиса, шифротекст AES-256-GCM | тот, у кого есть и БД, и `/var/lib/web-ssh/master.key` |
| cookie сессии | браузер | тот, у кого браузер |

Отзыв доступа к целевому хосту — **два действия, оба нужны**: удалить строку ключа из
`~/.ssh/authorized_keys` на хосте **и** удалить креды в интерфейсе. Пока креды есть в БД,
ключ живой.

Ротация: новый ключ (`ssh-keygen` с новым именем файла) → `ssh-copy-id` → новые креды в
интерфейсе → переключить хост на них → удалить старые креды → удалить старую строку из
`authorized_keys`. Только после последнего шага старый ключ мёртв.

Если инстанс смотрит в интернет:

- `known_hosts` не сверяется (ADR-007): при подключении к хосту в недоверенной сети ключ
  хоста принимается любой, MITM клиент не заметит. Для таких хостов сверяйте отпечаток
  руками (`ssh-keyscan -t ed25519 host`) и понимайте, что это ручная проверка, а не защита.
- Второго фактора на входе нет. Внешний периметр держится на basic-auth и rate limit прокси.
- Бэкап БД без `master.key` бесполезен, вместе с ним — равен SSH-доступу ко всем хостам.
  Не храните их в одном архиве и в одном месте.
